# 2026-09-06: the front end

Two pages. The brief scores architecture, pagination and documentation above feature count, so the
UI's job is to make the server-side work visible and then get out of the way.

## Prompt

> Next.js App Router, TypeScript. Two pages: a dashboard at `/` and an employee table at
> `/employees`.
>
> - Both are server components. They read the filter state out of `searchParams` and fetch from
>   the API on the server, so the browser never sees the API host and there is no CORS hop.
> - Filter state lives only in the URL. No client store, no `useEffect` fetching, no local copy of
>   the row data. A sorted, filtered, paginated view has to be a real address.
> - Sorting is a link. Paging is a link. The only client component is the filter bar, which pushes
>   a new URL, and it must reset `page` on every change.
> - No component library, no chart library, no Tailwind. Hand-written CSS, tabular numerals on
>   every number.
> - Show both the amount the person is actually paid and the USD equivalent, and only show the
>   native line when the two currencies differ.

## What I kept

The whole structure. Server components plus URL state is genuinely the least code here, not just
the most fashionable answer.

## What I rejected

- **TanStack Table.** Suggested immediately. It is a good library and it is for client-side
  sorting, filtering and paging, which is exactly the thing this exercise is scored on not doing.
  Pulling it in would have meant either fighting it to keep the work on the server, or quietly
  moving the work into the browser and losing the point.
- **A charting library for the breakdown.** Recharts was suggested for the spend-by-country view.
  A share-of-spend bar is a div with a percentage width. Two hundred kilobytes for eight bars.
- **`"use client"` on the page components**, with `useEffect` and `useState` to fetch. That is the
  default shape the assistant reaches for, and it would have put a loading spinner in front of
  data the server already had.
- **Debouncing the search box onto every keystroke.** It would fire a request per character
  against a `LIKE` scan. Enter submits, and that is a fine trade for one input.
- **`toLocaleString` on raw numbers.** Money arrives as a string on purpose. It gets parsed once
  in `lib/format.ts`, for display, and nowhere else.

## The bit I got wrong first

My first version of the filter bar kept `page` when a filter changed, so filtering from page 7
down to a two-page result showed an empty table. Fixed by having every filter change clear `page`,
which is one line in one place because all of them go through the same helper.
