# 2026-09-06 — review pass

Last thing before packaging. I asked for a critical read of the whole diff, the way I would ask a
colleague, and then went through the answers rather than applying them.

## Prompt

> Review this repository as a senior reviewer at a shop that cares about craft. Look for:
> correctness bugs, anything that would break at 10 million rows, layering violations where an
> inner layer imports an outer one, dead code, tests that could be flaky, and anything that is
> more abstraction than the problem needs. Rank by severity. Do not suggest features.

## What I acted on

- **The seed deleted the exchange-rate rows before the employee rows.** Foreign keys are on in the
  test fixtures, so re-seeding a populated database would have failed on the constraint. Real bug,
  found by a test that seeds twice. Children before parents now.
- **The test oracle rounded every row before summing.** The SQL rounds once, at the end, so
  `sum(round(x))` and `round(sum(x))` could disagree by a few cents and the test would have been
  quietly wrong rather than loudly failing. The oracle now mirrors what the database does.
- **Half-cent conversions.** One of my first exchange rates produced amounts landing exactly on a
  half cent, which rounds differently depending on whether the value went through a float first.
  On Postgres `NUMERIC` it never would, on SQLite it would, so the test would pass locally and
  fail somewhere else. Rates are now chosen so every converted salary is an exact number of cents,
  with a comment saying why.
- **A stray placeholder test** left in the analytics file with a `pass` body. Deleted.

## What I did not act on

- **"Add a `salary_usd` generated column and index it."** It would make sorting by pay an index
  scan instead of a sort, and it would freeze today's exchange rate into the table. When a rate
  changes, every stored value is wrong until something rewrites the column. The rate belongs in a
  join. If sorting by pay ever became the bottleneck the answer is a materialised view with an
  explicit refresh, not a hidden one.
- **"Cache `/employees/filter-options`."** Three `SELECT DISTINCT` queries on indexed columns
  against a table that changes never. Adding a cache adds an invalidation question and saves
  nothing measurable.
- **"Use `async def` routes and an async engine."** Same answer as at the start of the build.
  These are short analytic queries against a local database, and async would have bought nothing
  except a class of test-fixture problems.
- **"Extract a `BaseService`."** Two services with different dependencies and no shared behaviour.
- **"`app/domain/statistics.py` is unused, delete it."** It is used, as the oracle the SQL median
  is tested against. The docstring says so, precisely so the next reader does not delete it.

## Honest gaps

- No load test. The performance claims are a query plan on 10,000 rows and reasoning about what
  scales, not a benchmark at ten million.
- No CI pipeline. `make test` is the whole story.
- The web app has no automated tests. It is two server components that render what the API
  returns, the API is the part with the risk, and the time went there instead.
